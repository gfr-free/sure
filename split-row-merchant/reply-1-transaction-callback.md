Good catch, fixed in ff066a8. The callback now returns early unless `entry.may_have_split_rows?`, a new in-memory check on `Entry` (`excluded? && !split_child?`). Split parents are always excluded (`split!` sets it, and the drawer hides the exclude toggle for split parents), so ordinary transactions from syncs, imports, rules and drawer edits skip the child query entirely, with no extra round trip. `split_parent?` would have cost its own `EXISTS` query, so I avoided it. A new test asserts that no split-row query runs when a non-split transaction's merchant changes. The model tests now reload the parent before changing its merchant, because a transaction object kept from before the split still caches its pre-split entry. Real requests always load fresh records.
