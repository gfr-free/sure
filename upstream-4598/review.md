Thanks for looking into the flaky sidebar sparkline tests. I dug into where the flakiness comes from, and I think it is a real bug in the timeout wiring rather than a slow runner, so loosening the tests would hide it.

**What happens**

`AccountsHelper#sparkline_frame_data` clears the countdown on `turbo:frame-load`. Turbo's `FrameRenderer#render` inserts the new content after one `nextRepaint`, then awaits two more repaints before `turbo:frame-load` is dispatched. If the countdown expires inside that gap, `handleTimeout` overwrites the chart that has just been rendered, and nothing replaces the badge again. The frame ends up `complete`, not `busy`, and shows "Timeout" for good.

With the 300 ms test window this happens regularly (I logged it in the browser: the timeout fired after the response was inserted and before `frame-load`). In production it hits any sparkline whose response arrives just before the 10 s mark.

**Concern with this PR**

With the changes here, no test fails if the countdown is never cleared. I removed `turbo:frame-load->turbo-frame-timeout#clearTimeout` from `sparkline_frame_data` locally: the tests on main fail (2 failures), the tests on this branch all pass, although every sidebar sparkline would then turn into a "Timeout" badge 10 s after loading. Reverting the controller to start its timer in `connect()` is also caught by only one test instead of two.

**Suggested fix**

Stop the countdown when a successful response arrives instead of on `frame-load`:

```js
// turbo_frame_timeout_controller.js
responseReceived(event) {
  if (event.detail.fetchResponse.succeeded) {
    this.clearTimeout()
  }
}
```

```ruby
# AccountsHelper#sparkline_frame_data
action: "turbo:before-fetch-request->turbo-frame-timeout#startTimeout " \
        "turbo:before-fetch-response->turbo-frame-timeout#responseReceived",
```

Error responses (404/500) keep counting, so they still end in the badge as today. Since `account_sidebar_tabs` is cached with `skip_digest: true`, the cache version (`account_sidebar_tabs_v5`) would need a bump so cached markup picks up the new action.

For the tests, keeping the short window but waiting until no frame is in flight before checking for badges (`assert_no_selector "#{SPARKLINE_FRAME}[busy]", visible: :all, wait: ...`, then `wait_out_timeout_window`, then the existing no-badge assertion over all frames) removes the response-time requirement while still catching a countdown that is never cleared. The render gap itself can be tested deterministically by wrapping `event.detail.render` in `turbo:before-frame-render` and delaying `requestAnimationFrame` after the insertion, with a window long enough for the response to arrive first.

With that fix and those tests, the sparkline system tests passed 20 out of 20 runs locally, the render-gap test failed 5/5 on the current wiring, and the full suite was green.
