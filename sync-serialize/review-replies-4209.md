## Reply to jjmata, issue comment 6182210013 (hung holder keeps the lock) — POSTED https://github.com/we-promise/sure/pull/4209#issuecomment-6184819899

Post as a PR comment (quote or mention jjmata):

> Good catch, thanks for confirming the other three.
>
> Fixed in 3552a8f. When `Sync.clean` (the hourly `SyncCleanerJob`) marks a `syncing` sync stale, it now calls `Sync#release_hung_execution_lock`. That looks up the Postgres session holding the syncable's advisory lock in `pg_locks` and ends it with `pg_terminate_backend`, but only when that session has been idle (no statement running) for over an hour (`Sync::HUNG_LOCK_IDLE_AFTER`). A hung job is not running queries, while a sync that is actually working never sits idle that long, so a live holder is never cut off. This also covers a worker that crashed after its sync row went to `syncing` while a new sync now legitimately holds the lock: that holder is active, so it is left alone.
>
> Once the session is gone the lock is free and the waiting `SyncJob` runs on its next 30-second retry. If the hung job ever wakes up, its next query fails, `perform_sync` aborts, the sync stays stale and post-sync is skipped. Each release, or a failed attempt (for example a database role that may not signal the worker's session), is recorded as a `DebugLogEntry` in the `sync` category.
>
> So the worst case is now bounded by the existing stale window: about 24h plus up to one cleaner interval, instead of until a worker restart. I kept the 24h threshold on purpose so that "written off" means the same thing as everywhere else in `Sync`, and avoided a Ruby `Timeout` around `perform_sync` because interrupting provider code mid-write is riskier than ending an idle session.
>
> Tests in `test/models/sync_test.rb`: "clean ends a hung session still holding the lock of a sync it marks stale" (holds the lock from a second Postgres session, runs `Sync.clean`, asserts the session was terminated, the lock is free and the waiting sync then completes) and "clean leaves a lock holder alone while it is still running queries".

## Reply to CodeRabbit, review 5515899964, outside-diff comment on app/models/sync.rb ~230 (recheck the sync state after acquiring the lock) — POSTED https://github.com/we-promise/sure/pull/4209#issuecomment-6184820196

> @coderabbitai Fixed in 3552a8f. Right after `with_syncable_execution_lock` is acquired, `perform` now re-reads the sync (`refresh_after_lock`) and returns without `start!` when it is no longer `may_start?`, so a sync that was run by a duplicate job, cancelled or marked stale while the job waited is skipped instead of being moved back to `syncing`. The syncable-deleted and scheduled-for-deletion guards moved under the lock as well, and the re-read also picks up a window that a joined `sync_later` request widened in the meantime. The syncable instance the caller loaded is reloaded in place rather than dropped, so callers holding it keep working on the same object. Covered by "skips a sync that was finished elsewhere while it waited for the lock" and "runs with the window stored when it takes the lock, not the one it was loaded with".

> Fixed in 300be2bf8. If `pg_advisory_unlock` raises, `with_syncable_execution_lock` now calls `connection.throw_away!` before re-raising. That removes the connection from the pool and disconnects it, so the session (and any lock it still holds) is closed instead of being handed to the next job. Covered by "closes the session instead of pooling it when the lock cannot be released" in `test/models/sync_test.rb`.
